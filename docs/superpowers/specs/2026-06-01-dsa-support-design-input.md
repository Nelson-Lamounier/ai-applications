## 1. Recommended architecture

The product already has every structural primitive DSA needs. The design is overwhelmingly **reuse**, with one new ontology category, one new high-precision extractor, one JD-analysis output field, one JSONB field on company profiles, and one workspace section. DSA is *calibration + honest surfacing + gap acknowledgment* — never a practice platform.

**Data flow end-to-end:**

1. **Ontology (seed-time):** ~60-80 canonical DSA topics seeded into `technology_ontology` under a new `category='algorithm_pattern'` (or a dedicated small table — see §2). Structural only: name, category, prerequisites, jd_signal_keywords, source, as_of.
2. **GitHub scan (extract-time):** a new minimal `DsaPatternExtractor` (§3) emits **only high-precision import/type signals** into `technology_evidence` with `source_layer='dsa-pattern'`. These resolve via `OntologyResolver` to the seeded DSA canonicals.
3. **JD analysis (per-application):** the JD-parsing agent emits `dsaTopicCalibration` (§4) — which DSA topics the JD implies, with confidence and JD-quote evidence.
4. **Company-process (per-application):** `process_shape[].round_type` (§5) tells the workspace whether the Technical stage is `dsa | practical | take-home | system-design | mixed`.
5. **Workspace (render):** `TechnicalWorkspace` shows **Section A (system design)** + **Section B (DSA)**, gated by `round_type`, with the 🟢🟡🔴 evidence model (§6) joining JD calibration (what they'll test) × GitHub evidence (what your real work shows) × honest gap framing (where you must practice on LeetCode).

**Disagreement flag:** Surface-1 proposed the full 15-detector regex set wired into the orchestrator. The adversarial verdict rejected this. The architecture above adopts the **minimal high-precision** version (§3). This is the single biggest design fork the human must ratify.

## 2. Ontology review verdict

**Verdict: extend `technology_ontology` with one new `category` value — do NOT build a `dsa_problems`/`dsa_examples`/`dsa_study_plans` table.** The adversarial verdict (verdict #1, `holdsUp: false` on the "can't verify" framing but its *substance* is the binding guidance) is correct that the only honest shape is **constraint, not content**.

**Decision: new category over new table.** Both are defensible; recommend `category='algorithm_pattern'` on `technology_ontology` for v1 because:
- It reuses `OntologyResolver`, `technology_aliases`, and the whole resolve→`technology_candidates` fallback with zero new plumbing — the extractor's emitted `raw_name` (e.g. `dsa_graph_traversal`) resolves through the *exact same path* as a package name.
- DSA topics need aliasing (e.g. `bfs`, `breadth first search`, `level-order`) — `technology_aliases` already does this.
- **Caveat the human must weigh:** DSA topics are *concepts*, not technology artifacts. If mixing them into `technology_ontology` pollutes downstream consumers that assume "technology = installable thing" (skill graph, KB quality scoring), then a dedicated `dsa_topics` table (verdict #1's option 2) is cleaner. → **Open question in §8.** The `algorithm_pattern` category is reversible into a separate table later.

**Migration:** new `050_dsa_ontology.sql` (additive): `ALTER … CHECK (category IN (…, 'algorithm_pattern'))` on `technology_ontology`, then `INSERT … ON CONFLICT` seed rows.

**What to seed (structural columns only):**
- `canonical_name` (e.g. `dsa_graph_traversal`, `dsa_dynamic_programming`, `dsa_heap_priority_queue`)
- `category = 'algorithm_pattern'`
- `prerequisites` (JSONB array of other canonical_names — e.g. DP depends on recursion + memoization) *if added as a column; else defer to a `dsa_topics` table*
- `jd_signal_keywords` (JSONB array — e.g. `["latency","real-time","optimi"]` for complexity-sensitive roles) — drives §4 calibration
- `source` (citation: Tech Interview Handbook, NeetCode 150 topic taxonomy, Grokking patterns, interviewing.io topic frequency) + `as_of` (frozen snapshot)

**What to NEVER seed (the principle, made explicit):**
- ❌ Example problems ("Two Sum", LeetCode #1)
- ❌ Solutions or code snippets
- ❌ Filled-in study plans / day-by-day schedules
- ❌ Difficulty buckets as separate tables
- ❌ LeetCode URLs as content (a *single* "practice here" pointer in the UI is fine — it's a pointer, not stored content)

**"Reuse before create" check (from verdict #1):** Can DSA round expectations reuse `stage_expectations.focus_areas`? **Yes** — add `role_family='dsa'` (or `stage='technical-dsa'`) rows. Use that for "what the round tests." Use the new ontology category only for the *topic taxonomy + JD-signal mapping*. Do not duplicate `question_patterns` — it already encodes question-type hints without example content.

## 3. GitHub scanning (tech-extractor) verdict

**Verdict: build the MINIMAL high-precision detector, NOT the 15-topic regex set.** Adversarial verdict #2 (`holdsUp: false`) is decisive and grounded in the codebase's own discipline: the decommission report (`2026-05-27-decommission.md`) documents a **0–2.5% FP rate across 120 manually-inspected rows** and killed the LLM enricher's ~2% hallucination specifically because *honest structural grounding* is the product's core value. A 15-topic substring-regex extractor would regress FP to an estimated 10–20% (every nested loop ≈ "DP", every recursive function ≈ "recursive descent", every `deque` ≈ "graph traversal"). That is incompatible with the product.

**The honest-evidence test (the gate):** A signal is admissible only if a human can open the linked file/line and confirm the DSA *intent* without semantic inference. The match must be a *sufficient* condition, not merely necessary.

**Minimal HIGH-PRECISION detector set (admissible — these signal intent via the author's explicit library/type choice):**

| Signal | Pattern | Lang | Confidence | Why honest |
|---|---|---|---|---|
| Graph algorithms | `import networkx` (and use) | Python | 0.80 | networkx is a dedicated graph library — importing it is declarative intent |
| Heap / priority queue | `import heapq`, `from queue import PriorityQueue`, `java.util.PriorityQueue` | Py/Java | 0.78 | Dedicated priority-queue construct, not a generic loop |
| Tree structures | explicit `class TreeNode`, `BinaryTree`, `TrieNode` type defs | Multi | 0.75 | Author named a DSA type — explicit |
| Memoization (declarative) | `@functools.lru_cache`, `@cache`, named `memo`/`@memoize` decorator | Py/TS | 0.72 | Decorator name *is* the stated intent |
| Custom comparator sort | `sorted(…, key=)`, `Comparator.compare`, explicit `compareFn` | Multi | 0.70 | Explicit comparator authoring (still some FP — keep ≤0.70) |

**How a detection becomes honest evidence:** `DsaPatternExtractor` (implements `Extractor`, `Extractor.ts:7-10`) emits `RawTechnologyEvidence` with `raw_name='dsa_<topic>'`, `ecosystem='dsa_topic'`, `source_layer='dsa-pattern'`, `file_path`, `line_start`. It flows through the **unchanged** orchestrator resolve path into `technology_evidence` (RLS-protected per user). In the workspace it renders as **🟢 with a clickable GitHub file link** ("Your `pathfinder/graph.py:42` imports networkx — concrete graph-algorithm evidence you can talk to").

**What to EXPLICITLY NOT detect (these are necessary-not-sufficient → dishonest):**
- ❌ Sliding window via `for … range … len` / `[i:i+k]` slicing — matches any windowed/chunking/pagination loop
- ❌ "DP" via `dp[]` / nested loops — matches any 2D array iteration
- ❌ Recursion via "function calls itself" — matches FS traversal, JSON unmarshalling, GUI render
- ❌ Generic `deque` / `Queue` as "graph traversal" — it's a message queue more often than a BFS
- ❌ Set ops, rate-limiting, retry/backoff, pagination, generic stack via `list.append/pop`

**Confidence discipline:** Add `dsa-pattern` to `CONFIDENCE_BY_LAYER` at ≤0.80, *below* syft(0.95)/treesitter(0.85) and explicitly documented as "import/type-declaration grounded; NOT semantic confirmation of algorithmic use." Migration `050_dsa_source_layer.sql` adds `'dsa-pattern'` to the `source_layer` CHECK (`034:100`) and to `SourceLayer` in `techgraph.ts`.

**Parity caveat (verdict #2, must be honored):** The LLM enricher is **decommissioned** (`document_embeddings.technologies` returns `[]`). `ParityReporter` therefore CANNOT validate DSA signals against an LLM baseline — recall will read as "L1 finds DSA, LLM finds nothing," which is meaningless, not reassuring. **Gate before shipping:** run the 5-detector set against 3-5 real repos, hand-inspect every emission, require FP ≤ 5% (baseline + 2.5pp tolerance). If it can't hit that, drop the offending detector.

## 4. JD → DSA topic calibration

**Where it lives:** in the existing JD-parsing/research agent (`job-strategist`), emitted as a new structured field on the analysis output — *not* a new table, *not* the coach's free-text. This mirrors how the agent already extracts structured signals from a JD.

**Output schema (`dsaTopicCalibration`):**
```jsonc
{
  "dsaTopicCalibration": {
    "likelyTopics": [
      { "canonicalName": "dsa_graph_traversal",
        "displayName": "Graph traversal (BFS/DFS)",
        "confidence": 0.7,
        "rationale": "JD: 'build dependency resolution for the deploy graph'",
        "jdEvidenceQuote": "dependency resolution … deploy graph" }
    ],
    "calibrationBasis": "jd_signal_keywords matched against algorithm_pattern ontology",
    "honestyNote": "Inferred from JD language, not a guarantee of round content."
  }
}
```
- `confidence` is JD-inference confidence (separate axis from GitHub-evidence confidence in §3).
- Topics resolve to the seeded `algorithm_pattern` canonicals via `jd_signal_keywords` (§2).
- **Honest framing baked in:** the field is "likely topics implied by the JD," never "the topics they will ask."

## 5. Company-process gating

**How we know DSA vs practical vs take-home vs system-design:** extend `company_interview_profiles.process_shape` JSONB (`049:39`) with a per-stage `round_type`. The `ProcessStage` interface (`stage-prep-types.ts:32-36`) gains `readonly round_type?: 'dsa'|'practical'|'take-home'|'system-design'|'behavioral'|'mixed'`.

**Provenance:** per-company `round_type` is manually curated from Glassdoor reports / public eng blogs / interviewing.io aggregates, with the citation written into the migration's `source` field + `as_of` date (same discipline as comp benchmarks, which the memory note flags as "need to vet"). Migration `051_round_type.sql`: `jsonb_set` backfill, default `'dsa'` for safe mode.

**How it gates Section B (`TechnicalWorkspace.tsx`):**
```ts
const techRoundType =
  prep?.processShape?.find(p => p.stage.startsWith('technical'))?.round_type ?? 'dsa'
```
- `dsa` / `mixed` → render Section B (DSA) in full.

- `take-home` / `system-design` → suppress Section B's live-coding framing; Section A (system design) leads.
- Missing `round_type` → default `'dsa'` (safe mode — never hide DSA when uncertain).

**Coach calibration:** `round_type` is appended to the constraint block text by `buildStagePrepConstraintBlock` (`constraint-block.ts:65-103`) — text-only for v1, no `CoachAgentInput` schema change. **Disagreement flag (Surface-2 internal):** whether `round_type` is per-stage or one-per-company is unresolved — see §8.

## 6. Technical workspace

`TechnicalWorkspace.tsx` renders two sections under the existing `SectionHeading`/`Card` primitives.

**Data-sources banner (top of workspace, always visible):**
> "This prep combines: (1) what this company's technical round typically tests, (2) what your real GitHub work demonstrates, and (3) honest gaps where you should practice externally. DSA practice happens off-GitHub — we calibrate and point, we don't drill."

**Section A — System Design** (gated up when `round_type ∈ {system-design, take-home, mixed}`): unchanged conceptually from current architectural-discussion content.

**Section B — DSA**, each topic card carries an **evidence badge** joining §3 (GitHub) × §4 (JD):

- 🟢 **Grounded** — JD implies the topic AND high-precision GitHub evidence exists. *Card shows the file link from `technology_evidence`:* "You've shipped graph work — `repo/graph.py:42` (networkx). Be ready to talk through it."
- 🟡 **Partial** — JD implies it, but only weak/adjacent GitHub signal. "Likely on the JD; your code shows related but not direct evidence. Review before the round."
- 🔴 **Gap (honest)** — JD implies it, no GitHub evidence. **This is the product's honesty moment:** "This company likely tests dynamic programming. Your GitHub doesn't show DP work — that's expected, DP lives on LeetCode, not in production. Practice [NeetCode DP / LeetCode DP tag]." A pointer, not generated problems.

**Honest 🔴 framing rules:** never fabricate a "you sort of did this" story; never generate practice problems; always name the gap as *normal* (DSA practice isn't production work) and point externally. This is the explicit anti-pattern the positioning demands.

**Scope-down flag:** the existing `PracticeModal` (`TechnicalWorkspace.tsx:11`) has `PRACTICE_GENERATE` and `PRACTICE_MOCK` states. Per the positioning ("not a practice platform") these must be **demoted to external pointers** (link to LeetCode/NeetCode), not in-product generation/mock — see §7 defer list.

## 7. Decomposition

**Build now (priority order matches the ask):**
1. **JD→DSA categorization** (§4) — `dsaTopicCalibration` field in `job-strategist`; depends only on the seeded ontology. Highest leverage, lowest risk.
2. **Company-process taxonomy** (§5) — `round_type` on `process_shape`; migration `051` + `ProcessStage` field + workspace gate. Pure structural reuse.

5. **Honest gap framing** (§6) — 🟢🟡🔴 model + data-sources banner + 🔴 external-pointer copy.

**Build later (v1.5):**
- **Practice-repo archetype** — recognize a repo that *is* DSA practice (e.g. a `leetcode/` solutions repo) and surface it as legitimate prep evidence, distinct from production work.
- **DSA-tagged stories** — let users tag their stories/projects with the DSA topic they exercised, feeding 🟡→🟢 promotion.
- Phase-2 detector language coverage (Go/Java/Rust) *only if* the minimal set proves it can stay honest.

**Defer indefinitely (violates positioning):**
- ❌ Practice-problem generation (in-product) — demote `PRACTICE_GENERATE` to a LeetCode pointer.
- ❌ Mock interviews / in-product DSA tutoring — demote `PRACTICE_MOCK`.
- ❌ LeetCode API integration / problem-bank ingestion.
- ❌ The 15-topic regex detector set, `dsa_problems`/`dsa_examples`/`dsa_study_plans` tables, difficulty-bucket tables.

## 9. Honesty guardrails (where the design must not overclaim DSA competence)

1. **GitHub evidence is import/type-grounded, never semantic.** A 🟢 badge means "you imported networkx," never "you can solve graph problems in an interview." Copy must keep that distinction. (verdict #2)
2. **No `for`-loop / recursion / `dp[]` / generic-`deque` detection.** These produce dishonest evidence; explicitly excluded (§3). (verdict #2)
3. **Confidence ≤0.80 for `dsa-pattern`, documented as non-semantic** in `CONFIDENCE_BY_LAYER`. Do not let it read like syft/treesitter certainty. (verdict #2)
4. **FP-gate before shipping any detector** (≤5% on hand-inspected real repos); the LLM-parity safety net no longer exists. (verdict #2 — enricher decommissioned)
5. **Ontology stores constraint, never content** — no problems, solutions, study plans, difficulty banks. (verdict #1)
6. **🔴 gaps are framed as normal and pointed externally** — never fabricate "you sort of did DSA," never generate practice problems in-product. (positioning)
7. **JD calibration is "likely," never "guaranteed"** — `honestyNote` field is mandatory (§4).
8. **`round_type` defaults to `'dsa'` (safe mode)** — uncertainty must over-show DSA prep, never silently hide it (§5).
9. **Demote `PracticeModal` generate/mock to external pointers** — the product calibrates and points; it is not a practice platform.

**Net:** the architecture is almost entirely reuse of Spec-1 ontology discipline, tech-extractor's source-grounded evidence model, the JD-analysis agent, and `company_interview_profiles`. The two riskiest reviewer recommendations (15-topic regex detectors; any "content" DSA table) are **rejected** by the adversarial verdicts and replaced with the minimal high-precision detector + constraint-only ontology + honest 🔴 gap framing.
