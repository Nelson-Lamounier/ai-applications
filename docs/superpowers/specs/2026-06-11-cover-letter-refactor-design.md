# Cover-letter refactor — design

**Date:** 2026-06-11
**Status:** Approved (design) — pending plan
**Repos:** `ai-applications` (persona + guard + pipeline)
**Branch:** `feat/cover-letter-refactor` (stacked on `feat/years-gap` for `yearsGapFraming`)

## Problem

The cover letter is generated by the Sonnet writer's `<cover_letter>` block, which
has only FORMAT rules plus a truthfulness mandate that says *"flag gaps honestly"* —
so the letter actively undoes the resume:

- **Wrong title in the body** — it uses the archetype lead-identity ("User Operations
  Engineer") instead of the JD title ("AI Support Engineer"). The persona never tells
  it which string to use. Reads as a recycled/templated letter — the single fastest reject.
- **Contradicts the resume** — resume now leads with ~5 relevant years + "support
  engineer who ships production AI"; the letter opens "Three years triaging AWS
  escalations." 3 vs 5 — the reader doesn't know which is true.
- **Hands over the reject reasons** — "My 3 years… falls short of the 8-year threshold",
  "I do not yet have direct hands-on experience with ChatGPT/OpenAI API." It writes its
  own rejection. Root cause: the mandate mandates naming gaps.
- **Argues with the bar** — "I would be surprised if many 8-year candidates bring four
  production LLM systems." Tells the manager their criteria are wrong.
- **JD vocabulary absent** — SaaS troubleshooting, tickets/Slack/SLAs/response-times,
  cross-functional/Sales/Technical-Success/GTM, customer relationships, the named
  product/API — none surfaced.
- **Format kills the skim** — 5 dense paragraphs, heavy bold (keyword-stuffed look),
  differentiator buried in paragraph 3, opener is a windup not a hook. Claims unrealised
  impact ("pending security review").

## Three title concepts (kept separate — the core of the fix)

1. **JD title** ("AI Support Engineer") — used ONLY when naming the position applied to.
2. **Positioning headline** ("Technical Support Engineer · Cloud & AI Operations") — the
   resume `profile.title` / archetype `leadIdentity`: a *descriptive positioning*, NOT a
   job-title claim, so it never conflicts with the real AWS title.
3. **Employment titles** ("Technical Customer Service Associate") — verbatim in experience.

## Part 1 — persona `<cover_letter>` rewrite (prompt)

Replace the cover-letter rules with:
- **Title:** name the position using the exact `Target Role` (Research Brief) verbatim.
  NEVER use the archetype lead-identity or team name as the role title.
- **Align with the resume:** lead with the same differentiator as the resume's
  positioning headline; reflect the **YEARS GAP FRAMING** relevant-experience framing;
  never open with a single-role tenure that undersells ("3 years at AWS").
- **Never name, apologise for, or argue against any gap. OMIT gaps entirely.** Clarify
  the truthfulness mandate FOR THE COVER LETTER: truthful means never *fabricate*;
  *omission* of a gap is allowed and expected — the cover letter is never where you
  write your own rejection.
- **Surface JD vocabulary** — use the JD's exact requirement terms (SaaS troubleshooting,
  tickets/SLA/response-times, cross-functional/GTM/Technical-Success, customer
  relationships, the named product/API) WHERE a verified match or highlight supports it.
  Translate the candidate's real work into these terms; never claim what the evidence
  doesn't support.
- **Format:** open the first paragraph with a concrete hook (the rare capability /
  differentiator), not a windup. 3 tight paragraphs. Cap **bold** to ≤ 4 spans (company
  name + 1–2 strongest qualifications). Only **realised/shipped** impact — no "pending
  review" / not-yet-shipped claims.
- **Positioning headline rule (resume side):** `profile.title` (the archetype
  lead-identity) MUST be a positioning headline of the form `<Target-aligned role> ·
  <domain breadth>` (e.g. "Technical Support Engineer · Cloud & AI Operations") — a
  descriptive positioning, never a literal claim of holding the JD title.

## Part 2 — deterministic guard + Haiku rewrite (the guarantee)

New `applications/job-strategist/src/agents/cover-letter-guard.ts`:

```ts
interface CoverLetterViolation { code: string; detail: string; }

/** Deterministic checks. */
export function validateCoverLetter(letter: string, targetRole: string, leadIdentity: string): CoverLetterViolation[];
```
Checks (each a `code`):
- `missing_title` — the body does not contain `targetRole` (case-insensitive).
- `wrong_title` — `leadIdentity` ≠ `targetRole` AND the body contains `"${leadIdentity} role"` / `"${leadIdentity} position"` (using the lead-identity as the role name).
- `names_gap` — matches any self-rejection / gap-naming / bar-arguing regex:
  `/falls? short/i`, `/do(es)? ?n['’]?t yet have|do not yet have|have not yet|lack(ing)? (direct |hands-on )?experience/i`,
  `/\b\d{1,2}\s*years?\b[^.]{0,40}\b(short|threshold|bar|requirement|fall)/i`, `/I would be surprised/i`,
  `/while I (do ?n['’]?t|do not|have ?n['’]?t|lack)/i`.
- `too_bold` — count of `**…**` spans > 4.
- `unrealised_impact` — `/pending (security )?review|not yet (shipped|deployed|in production)|once (approved|shipped)/i`.

```ts
/** Haiku rewrite that fixes ONLY the listed violations. Fail-open → returns the input. */
export async function rewriteCoverLetter(letter: string, violations: CoverLetterViolation[], ctx: { targetRole: string; leadIdentity: string; yearsGapFraming: string }): Promise<string>;

/** Orchestrator: validate → rewrite if violations → return. Returns { letter, violations }. */
export async function guardCoverLetter(letter: string | null, targetRole: string, leadIdentity: string, yearsGapFraming: string): Promise<{ letter: string | null; violations: CoverLetterViolation[] }>;
```
- `guardCoverLetter`: if `letter` null/empty → `{ letter, violations: [] }`. Else
  `validate`; if violations → `rewrite` (Haiku, fail-open to the original) → re-`validate`
  (record any residual for telemetry) → return the rewritten letter + the ORIGINAL
  violations (for the metric).

## Part 3 — wiring (`run-pipeline`)

After `executeStrategistAgent` returns:
```ts
const { letter: finalCoverLetter, violations: coverViolations } = await guardCoverLetter(
  analysis.data.coverLetter,
  research.data.targetRole,
  analysis.data.archetypeSelection?.leadIdentity ?? '',
  yearsGap?.framingLine ?? '',
);
```
- A Prom counter `job_strategist_cover_letter_violations_total{code}` incremented per violation (telemetry — were violations caught/fixed).
- Use `finalCoverLetter` everywhere the cover letter is persisted/consumed: the
  `metadata.analysis` stash (`{ ...analysis.data, coverLetter: finalCoverLetter, … }`),
  `lintResumeProse(pool, env, tailoredResumeData, finalCoverLetter)`, and any
  DynamoDB/record write path.
- Fail-open: `guardCoverLetter` never throws; on rewrite error the original is kept.

## Testing
- `validateCoverLetter`: title present/absent; wrong-title (lead-identity-as-role);
  each gap-naming/arguing phrase; bold over/under cap; unrealised-impact phrase; a clean
  letter → no violations.
- `guardCoverLetter`: no letter → passthrough; clean → unchanged, no rewrite call;
  violations → calls rewrite (mocked) + returns the rewrite; rewrite throws → returns
  the original (fail-open) + the violations.
- run-pipeline: `finalCoverLetter` replaces the raw one in the stash + linter (assert
  the stash uses the guarded value); the metric increments.
- persona: a presence test that the new cover-letter rules + the positioning-headline
  rule strings are in the persona.

## Honesty
Omission is not dishonesty — the guard removes self-rejection/arguing and reframes via
the (true) yearsGap framing; it never adds a claim. The rewrite agent is instructed:
fix only the flagged issues, never introduce a new factual claim.

## Out of scope
- A separate cover-letter UI (the letter already renders in the app).
- Re-architecting the writer into a separate cover-letter call (the guard handles it post-hoc; a dedicated call is a later option if quality still lags).
