# Stage-Prep Reference Ontology — Design

> **Date:** 2026-06-01
> **Status:** Approved design (brainstorming complete). Implementation plan next.
> **Scope:** Spec 1 of 2. This spec builds the **stage-prep reference ontology**
> (global, frozen, versioned constraint data). Spec 2 — *Phone Screen end-to-end* —
> consumes it and is out of scope here.
> **Mirrors:** `migrations/046_project_ontology.sql` (the proven project-ontology pattern).
> **Supersedes nothing.** Implements build-item set from the
> `2026-05-31-stage-prep-program-reconciliation.md` program map (Steps 3 + comp).

## Why this exists

Stage prep is generated by LLM agents (the Coach Agent today). Without structural
constraints, the LLM invents the *scaffolding* of prep — what a stage tests, what
questions get asked, what a comp range is — alongside the *content*. That is exactly
the failure mode the project ontology (046) was built to prevent for case studies.

The rule, identical to the Projects decision:

> **Pre-seeded data is good when it is a structural constraint, bad when it is
> example content the LLM pattern-matches against.**

This ontology supplies *structural constraint*: "a Technical round at a FAANG-style
company typically tests distributed systems, system design, and language depth —
generate prep covering these areas **based on the user's evidence**." The LLM fills
slots; it does not invent the slots.

## What we build (structural constraint — good)

1. **Stage × role × company-type expectations** — what a stage typically tests.
2. **Common question *patterns* per stage** — question *types* (career arc, comp,
   conflict, ambiguity), not specific questions.
3. **Leadership-principle taxonomies per company** — public, finite, durable
   (Amazon's 16, Meta values, Google rubrics).
4. **STAR scaffold structures** — STAR / CAR / SAR templates (the LLM fills with the
   user's evidence).
5. **Compensation benchmarks** — role × seniority × region market ranges, sourced.
6. **Interview-process knowledge per company** — the *shape* of a company's process.
7. **Common-knowledge-gaps taxonomy** — gap-handling templates: how to gracefully
   acknowledge a 🔴 evidence gap and pivot to an adjacent strength.

## What we skip (example content — drives hallucination)

- "Top 100 questions to know in 2026" — primes the LLM to generate from a stale list.
- "Sample STAR stories for inspiration" — turns a story-*surfacer* into a story-*generator*.
- "What FAANG wants in 2026" commentary — prescriptive, conflicts with evidence-based positioning.
- Cached AI-generated per-company prep — not personalised, ages out.

## Architecture — 4 tables (grouped by lookup key)

The 7 build-items collapse into 4 tables grouped by *how they are looked up* and
*access pattern*, mirroring 046's instinct (related concepts sharing a table when they
share a key) without one-table-per-concept sprawl.

All tables are **global reference data**: no `user_id`, no RLS, frozen snapshot seeded
inside the migration via idempotent `INSERT ... ON CONFLICT DO UPDATE`. A future
upstream change is a new migration, never an in-place edit. This matches
`046_project_ontology.sql` exactly.

### Table 1 — `stage_expectations` (#1 expectations + #2 question patterns)

One lookup serves both "what the stage tests" and "what question types it asks".

```sql
CREATE TABLE IF NOT EXISTS stage_expectations (
    id                TEXT PRIMARY KEY,             -- 'faang|backend|technical-1'
    company_type      TEXT NOT NULL,                -- 'faang','scaleup','series-b','enterprise','*'
    role_family       TEXT NOT NULL,                -- 'backend','devops','frontend','ml','*'
    stage             TEXT NOT NULL,                -- InterviewStage enum value
    focus_areas       JSONB NOT NULL DEFAULT '[]'::jsonb,   -- #1 what it tests
    question_patterns JSONB NOT NULL DEFAULT '[]'::jsonb,   -- #2 question TYPES (not questions)
    expectation_note  TEXT,                         -- prose constraint injected into prompt
    source            TEXT NOT NULL,                -- citation
    as_of             DATE NOT NULL,
    UNIQUE (company_type, role_family, stage)
);
```

`question_patterns` row shape: `[{ "type": "career-arc", "prompt_hint": "..." }, ...]`.

### Table 2 — `company_interview_profiles` (#3 leadership principles + #6 process + values)

```sql
CREATE TABLE IF NOT EXISTS company_interview_profiles (
    company_key           TEXT PRIMARY KEY,         -- 'amazon','stripe','meta'
    display_name          TEXT NOT NULL,
    company_type          TEXT NOT NULL,            -- joins to stage_expectations dimension
    leadership_principles JSONB NOT NULL DEFAULT '[]'::jsonb,   -- #3 [{name,description}]
    process_shape         JSONB NOT NULL DEFAULT '[]'::jsonb,   -- #6 ordered [{stage,format,note}]
    values_taxonomy       JSONB NOT NULL DEFAULT '[]'::jsonb,
    source                TEXT NOT NULL,
    as_of                 DATE NOT NULL
);
```

### Table 3 — `prep_scaffolds` (#4 STAR/CAR/SAR + #7 gap-handling templates)

Both are "templates the LLM fills" — distinguished by `kind`.

```sql
CREATE TABLE IF NOT EXISTS prep_scaffolds (
    id        TEXT PRIMARY KEY,                     -- 'star','car','sar','gap-adjacent-pivot'
    kind      TEXT NOT NULL CHECK (kind IN ('story_scaffold','gap_handling')),
    title     TEXT NOT NULL,
    structure JSONB NOT NULL DEFAULT '{}'::jsonb,   -- STAR: {steps:[...]}; gap: {trigger,template}
    source    TEXT NOT NULL,
    as_of     DATE NOT NULL
);
```

### Table 4 — `comp_benchmarks` (#5)

```sql
CREATE TABLE IF NOT EXISTS comp_benchmarks (
    id          TEXT PRIMARY KEY,
    role_family TEXT NOT NULL,
    seniority   TEXT NOT NULL CHECK (seniority IN ('junior','mid','senior','staff','principal')),
    region      TEXT NOT NULL,                      -- 'eu-remote','us','uk','emea'
    currency    TEXT NOT NULL,
    range_min   INT NOT NULL,
    range_p50   INT NOT NULL,
    range_max   INT NOT NULL,
    source      TEXT NOT NULL,
    as_of       DATE NOT NULL,
    UNIQUE (role_family, seniority, region)
);
```

## Selection logic — the `'*'` sentinel fallback

`stage_expectations` is resolved by an ordered fallback so a small set of
company-type-specific overrides sits on top of a generic decade-stable base layer.
This keeps "full seed" tractable (~50–100 rows total, not the full
company × role × stage cartesian product):

1. exact `(company_type, role_family, stage)`
2. → `('*', role_family, stage)`
3. → `('*', '*', stage)`

Supporting resolution:

- **`role_family`** — map `targetRole` string → family via a keyword map (reuse any
  existing role mapping; otherwise a small deterministic map in the new module).
- **`company_type`** — resolve `targetCompany` → `company_interview_profiles.company_key`
  → its `company_type`; else `'*'`.
- **`seniority`** — reuse the existing `pickStage()` over profile-rollup
  `direction.seniority`; map its `junior|mid|senior|staff` to the comp seniority enum
  (adding `principal` at the top).
- **`region`** — a lookup input supplied by the caller (Spec 2 derives it from JD /
  user location; this spec only provides the query path).

`comp_benchmarks` uses the **same `'*'` role fallback**: exact `(role_family, seniority,
region)` → `('*', seniority, region)`. This is forced by the data — free comp sources
(levels.fyi public pages) only publish generic "Software Engineer" figures for EU/UK,
not per-role. Generic rows are stored with `role_family='*'` and labeled as such in
`source`; only US has real role-split data (Stack Overflow 2025 medians). We never
duplicate a generic number under multiple role labels to fake role precision.

## Consumption contract — `applications/shared/src/stage-prep/`

New shared module exposing the ontology as a typed repository:

```
RdsStagePrepOntologyRepository
  getStageExpectation(companyType, roleFamily, stage)  // sentinel fallback baked in
  getCompanyProfile(companyKey)
  listScaffolds(kind)                                   // 'story_scaffold' | 'gap_handling'
  getCompBenchmark(roleFamily, seniority, region)
```

**Boundary decision (deliberate divergence from 046):** This spec ships the **data
layer only** — migration + seed + repository + selection helpers + tests. The
prompt-injection block builder (`buildStagePrepConstraintBlock`) and the Coach Agent
wiring live in **Spec 2 (Phone Screen)**, where they have a live consumer.

Rationale: 046's `project_stage_overlays.stage_suggestions` was built and fetched but
never injected into a prompt — a stranded rail. We avoid repeating that: the
repository API is the tested contract this spec delivers; Spec 2 consumes it live.

## Provenance & freezing discipline

- Every row carries `source` (e.g. Glassdoor, levels.fyi, Stack Overflow Developer
  Survey, official company leadership-principle pages) and `as_of`.
- The migration header cites the curation sources + a version string + the line
  *"Frozen snapshot: a future upstream change is a new migration."* — verbatim to 046.
- No versioning columns; freezing is by migration snapshot + idempotent upsert.

## Seed breadth

Full seed of all 7 items in this PR:

- `stage_expectations` — generic `'*'` base rows for every stage, plus company-type
  overrides for the major `(company_type, role_family, stage)` combinations (~50–100 rows).
- `company_interview_profiles` — a curated set of well-documented companies (incl.
  Amazon's 16 leadership principles, Meta + Google values, process shapes).
- `prep_scaffolds` — STAR / CAR / SAR `story_scaffold` rows + a set of `gap_handling`
  templates ("if you've used Y in similar patterns, acknowledge the X gap and pivot").
- `comp_benchmarks` — a sourced starter set across role_family × seniority × region,
  each row citing its source + `as_of`.

Rows with no Phone-Screen consumer (leadership principles, STAR scaffolds) are still
seeded now but proven later by the Behavioural / Bar-Raiser stages.

## Placement & migrations

- New file `applications/platform-rds-bootstrap/migrations/049_stage_prep_ontology.sql`.
- Loaded by the existing `runBootstrap` lexicographic migration runner — no change to
  `bootstrap.ts` DDL (reference data lives in migrations, per 046; bootstrap DDL is for
  base operational tables).
- Global tables: no `user_id`, no RLS (mirror `technology_ontology` / `project_archetypes`).

## Testing

- **Unit** — sentinel fallback ordering, `role_family` keyword mapping, seniority→comp
  enum mapping, comp lookup, scaffold filtering by `kind`.
- **Integration** — migration applies cleanly; all four tables queryable; seed row
  counts > 0; a representative `getStageExpectation` resolves through each fallback tier.
