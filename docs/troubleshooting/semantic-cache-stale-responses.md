## Symptom

Operators or users report one of:

- "I asked about X but got the answer for Y" — the response is
  coherent but unrelated to the current query.
- Answers reference an old KB revision (e.g. quoting documentation
  that was deleted last week).
- Two users in different scopes see each other's cached answers.
- A model swap landed but the cache still returns outputs that
  read like the old model.
- `hit_count` on a small set of rows climbs disproportionately
  high — same near-miss rows keep matching.

The semantic cache schema is `(scope, kb_tag, query_text,
query_embedding, response, hit_count, created_at)` indexed by HNSW
on `query_embedding` and a B-tree on `(scope, kb_tag, created_at)`
([applications/platform-rds-bootstrap/migrations/022_semantic_cache.sql](../../applications/platform-rds-bootstrap/migrations/022_semantic_cache.sql)).

## Root cause

Four mechanisms produce this symptom, all distinct:

1. **Threshold too low.** Default similarity threshold is `0.95`
   ([pg-semantic-cache.ts:54-55](../../applications/shared/src/cache/pg-semantic-cache.ts#L54-L55))
   set via `SEMANTIC_CACHE_THRESHOLD`. If overridden lower (say
   `0.85`) the cache hits on "similar but distinct" queries.
2. **`kbTag` not bumped after a model swap or KB reindex.**
   `kbTag` is the platform's free-invalidation primitive
   ([CONTEXT.md lines 19-21](../../CONTEXT.md)). Forgetting to
   rotate it strands old responses behind the same lookup key —
   responses outlive the model/KB they were valid against.
3. **Scope collision.** Two distinct app paths share the same
   `scope` string. The cache cannot distinguish them; one writes,
   the other reads. The schema does not enforce scope uniqueness
   per caller.
4. **TTL too long for the workload.** Default 7-day TTL
   ([pg-semantic-cache.ts:56-57](../../applications/shared/src/cache/pg-semantic-cache.ts#L56-L57))
   keeps a response alive a week. If the underlying knowledge
   changes every two days, day-three answers are stale.

## How to diagnose

### 1. Reproduce the bad hit deterministically

Open `psql` against the cache database and replay the query the
user complained about. Match by `scope` + the cached `query_text`
field (which is the PII-scrubbed, normalised form,
[pg-semantic-cache.ts:118](../../applications/shared/src/cache/pg-semantic-cache.ts#L118)):

```sql
SELECT id, scope, kb_tag, query_text, hit_count, created_at,
       1 - (query_embedding <=> (
         -- Use Titan to embed the user's actual query, paste the
         -- vector literal here or compute via the embedder service.
         '[<1024 floats from Titan v2>]'::vector
       )) AS similarity
FROM semantic_cache
WHERE scope = 'chatbot_rag'
ORDER BY query_embedding <=> '[<floats>]'::vector
LIMIT 5;
```

The top row is what the cache returned. Inspect:

- **Its `similarity`** vs `SEMANTIC_CACHE_THRESHOLD` (default `0.95`)
- **Its `kb_tag`** vs the caller's *current* `kbTag` constant
- **Its `created_at`** vs `NOW() - INTERVAL '7 days'`
- **Its `query_text`** — does it actually describe the user's intent?

### 2. Identify which mechanism

| Diagnostic | Mechanism |
| :- | :- |
| Top row's `similarity` is between `0.80` and `0.95` and the threshold env var is overridden lower | (1) Threshold too low |
| Top row's `kb_tag` differs from the caller's current `kbTag` | (2) `kbTag` not bumped — old rows still matching |
| Top row's `query_text` makes sense for a *different* app's flow | (3) Scope collision |
| Top row's `created_at` is older than the platform change that should have invalidated it, and `kb_tag` was not rotated | (2) — same as above |
| Top row's `hit_count` is high but the rows below it are unrelated | (1) — and the bad row's been a stable false positive |

### 3. Cross-check the caller wiring

Search for the caller's `kbTag` constant:

```bash
grep -rn "kbTag" applications/chatbot/ applications/job-strategist/ \
  applications/shared/src/cache/ --include="*.ts"
```

Typical pattern: a `KB_TAG` constant at module top, formatted
`<kb-version>:<model-id>` or `<kb-version>:<retrieval-revision>`.
If the model was upgraded (e.g. Sonnet 4.5 → 4.6) and the constant
was not bumped, every cached response was generated by the old
model and the new model's caller is reading them as if they were
fresh.

### 4. Check scope distribution

```sql
SELECT scope, COUNT(*) AS rows, MIN(created_at), MAX(created_at)
FROM semantic_cache
GROUP BY scope
ORDER BY rows DESC;
```

Two scope names that look near-identical (e.g. `chatbot_rag` and
`chatbot-rag`) are a strong scope-collision smell — unify them via
a code change.

## How to fix

### Mechanism 1 — threshold too low

Restore to default in the caller env (or in the constructor
`extra.threshold` arg):

```bash
# Deployed envs
kubectl -n <ns> set env deployment/<app> SEMANTIC_CACHE_THRESHOLD=0.95
```

Then evict the rows that should never have hit at `0.95`:

```sql
-- Delete rows that hit between the wrong and right threshold
DELETE FROM semantic_cache
WHERE scope = 'offending_scope'
  AND hit_count > 0
  AND id IN (
    -- subquery identifying the false-positive rows by inspection
  );
```

In practice it is faster to wipe the scope and let it refill:

```sql
DELETE FROM semantic_cache WHERE scope = 'offending_scope';
```

The cache is fail-open; users see a few hundred milliseconds of
extra Bedrock latency during refill, no error.

### Mechanism 2 — `kbTag` not bumped

The fix is in code. Update the `KB_TAG` constant on the calling
side to encode the new model / KB version. Old rows are now
unreachable (they sit at the old `kbTag`) and the 7-day TTL evicts
them passively
([pg-semantic-cache.ts:90-92](../../applications/shared/src/cache/pg-semantic-cache.ts#L90-L92)
— the `created_at > NOW() - ($5 || ' days')::interval` clause).

If you want them gone now:

```sql
DELETE FROM semantic_cache WHERE kb_tag = '<old-tag>';
```

This is the canonical *invalidation-on-version-change-for-free*
pattern. Bumping `kbTag` should be part of any code change that
makes prior responses misleading.

### Mechanism 3 — scope collision

Pick the canonical scope name. Update the code on the wrong side.
Wipe the colliding rows:

```sql
DELETE FROM semantic_cache WHERE scope = 'wrong_variant';
```

If both scopes have legitimate caches that you want to keep,
rename one to a non-colliding name (e.g.
`chatbot_rag_public` vs `chatbot_rag_authenticated`) and migrate
the row prefix:

```sql
UPDATE semantic_cache SET scope = 'chatbot_rag_public'
WHERE scope = 'chatbot_rag' AND <discriminator-condition>;
```

### Mechanism 4 — TTL too long

Lower in env:

```bash
kubectl -n <ns> set env deployment/<app> SEMANTIC_CACHE_TTL_DAYS=3
```

The change applies on next pod start; existing rows continue to
respect their `created_at` until the cache-read TTL clause excludes
them ([pg-semantic-cache.ts:90-92](../../applications/shared/src/cache/pg-semantic-cache.ts#L90-L92)).
A lower TTL does not delete rows — the TTL is read-side filtering.
For real cleanup:

```sql
DELETE FROM semantic_cache
WHERE created_at < NOW() - INTERVAL '3 days';
```

## How to prevent

- **Treat `kbTag` as code under version control.** Every code change
  that affects what the cache "should" return — model swap, KB
  reindex, prompt change that materially shifts answers — must bump
  the `kbTag` constant at the call site. PR reviewers should look
  for this; a code change without a `kbTag` bump for a behaviour-
  affecting change is a defect.
- **Scope names should be globally unique strings, not parameters.**
  A scope name is the metric label
  ([cache-types.ts:30-38](../../applications/shared/src/cache/cache-types.ts#L30-L38))
  AND the cache key component AND the diagnostic anchor. Choosing it
  badly (collision, ambiguity) costs you in three places. A constant
  `const SCOPE = 'chatbot_rag_public'` at the calling module's top
  is the right pattern; an inlined string is not.
- **Hit-rate dashboards split by scope.** A scope's hit rate
  *dropping* may be expected (fresh `kbTag`); a scope's hit rate
  *climbing without bound* on a small `query_text` set is the
  false-positive signal — a few rows getting hammered while the rest
  of the table sits idle. The `hit_count` column makes this
  observable per row.
- **Default threshold conservatism.** `0.95` is high enough that
  hits are near-identical queries. Lowering it without a clear hit
  rate target *and* a manual sample of would-be additional hits is
  begging for this incident.
- **Bound TTL by the volatility of the underlying knowledge.** A 7-day
  default is right for a documentation-style KB. For a KB that
  changes hourly, 7 days is wrong on day one. Set `SEMANTIC_CACHE_TTL_DAYS`
  per-app accordingly.
